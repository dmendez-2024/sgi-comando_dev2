1. En DBeaver, conectarse a la base PostgreSQL usada por el backend de SGI Comando.
   Ejecutar 04_diagnosticar_supervisor.sql. Si la conexión quedó en una transacción
   fallida (25P02), ejecutar ROLLBACK antes de repetir el diagnóstico.

2. Abrir 05_habilitar_supervisor_operador.sql. Username predeterminado: supervisor;
   compañía predeterminada: Galvarino. Si ya hay vínculo al empleado correcto,
   el script comprueba además el nombre de Ciro. Si no hay vínculo,
   completar UNO con la identidad real encontrada en el diagnóstico 04.
   Ejemplo: reemplazar NULL::bigint AS persona_id por 1234::bigint AS persona_id
   SOLO si 1234 es el personas.id confirmado de esa persona en SIC/RRHH.
   No elegir al primer supervisor de la lista ni inventar un empleado.

3. Ejecutar el archivo 05 COMPLETO en una sola sesión (DBeaver: ejecutar script).
   La transacción activa la cuenta, fija SUPERVISOR_SEGURIDAD, añade el alcance
   COMPANY y crea/reactiva el vínculo empleado. Conserva la contraseña existente.
   Aborta ante identidad, tenant, membresía, alcance o vínculos contradictorios.
   No crea fichas RRHH ni turnos. Es repetible para la misma identidad.

4. En el servidor de SGI Comando debe estar SGI_OPERATOR_RELIEF_UAT_ENABLED=true.
   Esta opción controla la API del operador, no es un permiso de base de datos.
   Si cambia la variable, recrear/reiniciar el backend con la configuración aplicada.

5. Volver a iniciar sesión en SGI Operador con la contraseña propia del supervisor.
   Verificar la respuesta autenticada de GET /api/v1/operator/runtime en el backend
   configurado en esa app (puede llevar un prefijo de proxy, por ejemplo /dev.comando).
   Esta API usa Basic con username y contraseña de app_user.
   Si responde con employeeId y assignments=[], la cuenta tiene acceso pero no hay
   turno utilizable en ese momento. Publicar la asignación de esa persona desde
   Asignaciones; no copiar las asignaciones del agente. El runtime prioriza turnos
   actuales y, si no hay, el más cercano dentro de los siguientes 59 minutos.

Diagnóstico por respuesta HTTP:
- 401: revisar contraseña, username, servidor y Authorization Basic. Asignar un
  rol no cambia una contraseña incorrecta. Para restablecerla, puede colocar un
  bcrypt MCF nuevo en new_password_hash del script 05; nunca texto plano.
- 403: leer el mensaje: usuario inactivo/otro tenant, rol, vínculo o asignación.
- 404: si el mensaje dice Integración de relevo UAT deshabilitada, activar la
  variable del punto 4. Si es un 404 del proxy, comprobar URL/prefijo de la app.
- 5xx: revisar backend/integraciones; un cambio de roles puede no resolverlo.

El formulario de acceso de SGI Operador está en otro proyecto. Estos scripts
configuran su acceso al backend SGI Comando; no modifican ese formulario.
